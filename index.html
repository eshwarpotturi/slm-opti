The five layers

The model understands language well and is careless with details. So code does the careful parts, and the model does only the language part. Each layer runs in this order on every request.

  1. Repair and check the format

    Fixes a malformed reply and checks it against a template built from the tool list. One retry.

    StopsA correct action written so that a program cannot read it.

  2. Show only the right records

    Finds the customer or ID named in the request. The model sees only those records and can only use their IDs.

    StopsCancelling another customer's invoice. Invented IDs.

  3. One request at a time, few tools

    Splits a message wherever a new customer or ID appears, and shows the model the handful of relevant tools out of 23.

    StopsDoing half of a two-part message. Picking a lookalike tool.

  4. Check every action against the rules

    Before anything runs, code checks it against the account. A rejected action goes back with the reason once, then is dropped.

    StopsRefunding an order twice. Reminding a customer who has paid. Making up an amount.

  5. Hand off when unsure

    The small model answers three times. If the answers disagree, or a rule fired, a large model takes that request.

    StopsThe remaining hard cases. of 150 requests were handed off.

What each layer added, on three small models

Share of 150 requests handled correctly, layers 1 to 4. These are the development requests the code was built against, so the levels run high; the shape is the point.

Making replies readable (layers 1 to 3) can make a model act more often, wrongly too. On Llama 3.1 8B, wrong actions rose from to after layer 1, and fell to once the rule check was added.

What this does not show

  • A large model alone on the same requests has not been measured, so there is no reference line yet.
  • The rules in layer 4 and the tests were written by the same author. The requests here use new accounts and another model's wording, but the kinds of request are the same.
  • Layer 1 repairs and validates a reply after the fact. It is not grammar-constrained decoding.
  • Every account, customer and transaction is invented. Nothing is executed; the test checks which actions the model proposes.
  • Marking is exact. A harmless extra lookup counts as wrong.

To measure this on your own tools

Three things are enough to produce the same ladder for your system:

  • The list of actions your assistant can take, with their fields.
  • A few hundred real requests with the action that should have followed, names removed.
  • The rules an action must pass before it runs. Layer 4 is where they go.
